Take the existing approved NovaSport frontend and move the application from prototype/mock-data mode to a real production-ready application using our serverless architecture and Supabase as the backend. Do not redesign the approved UI unnecessarily. Treat the current frontend, navigation, user journeys, and established NovaSport design system as the approved product specification. Your task is to connect that experience to real authentication, database records, storage, permissions, and server-side operations, while making only the frontend adjustments necessary for the real data and workflows.

First, audit the entire existing application and identify every source of mock data, hardcoded record, simulated API response, fake statistics, placeholder user, local-only state, temporary fixture, and prototype action. Map each one to the appropriate real Supabase entity or backend operation before replacing it. Do not simply remove mock data and leave broken screens; every important screen must have a real loading, empty, error, success, and offline state. There must be no fabricated teams, players, fixtures, statistics, users, competitions, or dashboard numbers in the live application.

Establish Supabase as the single source of truth for NovaSport data. Use Supabase Auth for authenticated accounts, PostgreSQL for relational data, Storage where images or documents are genuinely required, and serverless/Edge Functions for operations that should not be trusted to the client, such as privileged administrative actions, fixture generation, approvals, publishing, or other business-critical workflows. Design the database around reusable records rather than duplicated frontend objects: competitions, seasons, teams, people/accounts, player profiles, coach assignments, roster memberships, officials, fixtures, appointments, match events, results, standings, statistics, news/content, and relevant approval/status records. A team should be created once and reused across competitions; a player should have one central identity and reusable history; people should not receive duplicate accounts simply because they have multiple roles.

Implement the approved NovaSport admin workflows against the live backend. Administrators must be able to register and approve teams, edit approved team information, assign coaches, manage competition participation, review coach-submitted player invitations, approve or reject players, manage approved officials, appoint match officials, create competitions, create and manage seasons, add approved teams to a season, generate fixtures, manually create or edit fixtures, manage postponements and cancellations, and review results. Every action must persist to Supabase and immediately reflect anywhere else in NovaSport where that information is legitimately used.

Connect the Overview, Leagues & Seasons, Teams & Rosters, Official Directory, and Match Official sections to real data. The Overview must calculate its information from current backend records rather than static dashboard values. Leagues & Seasons must use real competition and season records and enforce the rule that a competition can have only one active season at a time while retaining historical seasons. Teams & Rosters must distinguish the permanent team record from its participation in a particular competition and season. Official Directory must reuse the same person/account records used elsewhere. Match Official must create real fixture appointments linked to existing officials and fixtures rather than duplicating official information.

Implement the complete registration and approval chain. An administrator creates or reviews a team registration and approves the team before it becomes eligible for competition participation. A coach can invite or nominate a player through the coach workspace; that request becomes a real pending approval visible to the appropriate administrator. When approved, the system creates or activates the correct roster membership for the relevant team and season while reusing the existing player record. Prevent duplicate player identities and duplicate active memberships according to the application's business rules. Rejections, corrections, removals, transfers, and historical memberships must preserve appropriate history rather than overwriting important records.

Implement real competition and fixture management. Creating a league or tournament should create a reusable competition record. Creating a season should associate it with that competition. Adding teams to the season must select from approved existing teams rather than creating new team records. Fixture generation should be implemented as a controlled backend operation: validate the selected participating teams and scheduling parameters, generate the proposed fixtures, return a preview, and only persist them after administrator confirmation. Provide a reliable manual fallback for creating, editing, rescheduling, postponing, or cancelling individual fixtures. Do not put complex fixture-generation logic directly in the client where it can be manipulated or inconsistently executed.

Implement proper authorization and Row Level Security. Never rely on hiding buttons in the frontend as the security model. Define the intended roles and permissions for administrators, coaches, players, match officials, and other authorized users, and enforce access at the backend/database/serverless-function level. An authenticated user should only access data and perform actions appropriate to their role and authorized context. Administrative actions must be protected server-side. Review every Supabase table and relationship for appropriate RLS policies before considering the integration complete.

Connect the backend to the rest of NovaSport, not only the admin application. Approved teams must appear correctly on public team and competition pages. Approved player memberships must flow into rosters and public player/team views where appropriate. Fixtures created in administration must appear in the relevant competition schedule and Match Centre. Verified results must feed the appropriate standings and statistics workflows. Official appointments must appear in the relevant match and official workspaces. Changes must propagate through the shared data model instead of requiring separate manual updates in different parts of the application. Maintain a clear distinction between private administrative information, pending information, verified information, and publicly published information.

Review the frontend while performing the integration and make practical adjustments where the prototype assumed mock data. Replace fake interactions with real asynchronous operations, proper optimistic or confirmed updates where appropriate, query invalidation/refetching, server-side validation feedback, confirmation dialogs for consequential actions, and meaningful success/error messages. Do not allow the UI to imply that an operation succeeded until the backend has actually confirmed it. Handle slow connections, failed requests, expired sessions, empty datasets, deleted or unavailable records, and offline states gracefully. Public data that is cached for offline use must display appropriate freshness information and must never be presented as newly updated live data when it is not.

Do not create unnecessary APIs, duplicate tables, or parallel data models merely to make the frontend easier to connect. Reuse the existing architecture where it is sound, and refactor prototype code where necessary. Where the current database schema cannot correctly represent a required NovaSport relationship, stop and document the required schema change rather than creating a workaround that introduces duplicate records or inconsistent state. Keep business rules centralized and predictable.

Before declaring the application live, test the complete real-data journeys end to end: authenticate an administrator; register and approve a team; assign a coach; create or select a competition; create its active season; add the approved team; allow a coach to invite a player; approve the player; confirm the roster updates; generate fixtures; manually adjust a fixture; appoint an official; record and verify a result; confirm that the result reaches the correct competition, team, match, standings, and statistics views; and verify that public-facing pages display only the information they are supposed to display. Test rejection, cancellation, duplicate, permission-denied, validation-error, empty-state, and network-failure scenarios as well.

The final result should be a real NovaSport application, not a frontend demo connected to a database. Remove mock data completely, connect the approved design to Supabase, enforce the actual relationships and permissions, preserve data integrity, and ensure that one change to a canonical record is reflected throughout the appropriate NovaSport experiences. Keep the product minimal and operationally simple: the complexity should live in the architecture and business rules, not in the administrator's interface.
